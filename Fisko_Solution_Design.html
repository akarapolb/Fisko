01บทนำ

อธิบายวัตถุประสงค์ ขอบเขต และวิธีอ่านเอกสาร

1.1วัตถุประสงค์ของเอกสาร

Fisko คือชื่อแพลตฟอร์ม ส่วน AEBMS (Agency e-Budgeting Management System) คือชื่อระบบที่ใช้ในเอกสารข้อกำหนด เอกสารนี้ใช้ทั้งสองชื่อในความหมายเดียวกัน

เอกสารนี้กำหนดการออกแบบโซลูชันของ Fisko ครอบคลุมฟังก์ชันการทำงาน สถาปัตยกรรมแอปพลิเคชัน สถาปัตยกรรมเทคนิค ข้อมูล การเชื่อมต่อ AI และความมั่นคงปลอดภัย เพื่อใช้เป็นฐานร่วมกันระหว่างหน่วยงานและทีมพัฒนาก่อนจัดทำ Functional Requirement Specification และ Detailed Design รายโมดูล

1.2ขอบเขต

อยู่ในขอบเขตนอกขอบเขต
  • วงจรงบประมาณระดับหน่วยรับงบประมาณ ตั้งแต่แผนยุทธศาสตร์ถึงการประเมินผลสัมฤทธิ์ (M01–M08)
  • AI และการวิเคราะห์เพื่อสนับสนุนการตัดสินใจ (M09)
  • การบริหารข้อมูลหลัก โครงสร้างงบประมาณ สิทธิ์ และ Workflow (M10)
  • การเชื่อมต่อกับระบบภายนอกตามช่องทางที่ได้รับอนุญาต
  • การย้ายข้อมูลงบประมาณย้อนหลังเพื่อการเปรียบเทียบ
  • การบันทึกบัญชีและการเบิกจ่ายจริง ซึ่งยังทำในระบบบัญชีภาครัฐ
  • กระบวนการจัดซื้อจัดจ้าง
  • การบริหารงานบุคคลและเงินเดือน
  • การแก้ไขระบบของสำนักงบประมาณหรือหน่วยงานภายนอก

02ภาพรวมโซลูชัน

One Budget Platform: From Strategic Planning to Budget Performance

2.1หลักการออกแบบ

P1
Integrated Budget Managementข้อมูลชุดเดียวตั้งแต่แผนถึงผล ไม่บันทึกซ้ำระหว่างหน่วยงาน
P2
Strategy-Driven Budgetingทุกคำขอผูกกับแผนงาน ผลผลิต ตัวชี้วัด และยุทธศาสตร์
P3
Collaborative Budget Planningหลายระดับทำงานบน Workflow เดียว พร้อมประวัติทุกรอบ
P4

P5
AI-Assisted BudgetingAI ช่วยร่าง ตรวจ และวิเคราะห์ ส่วนการอนุมัติเป็นของผู้มีอำนาจ

2.3สมมติฐานและข้อจำกัด

  • ปีงบประมาณเริ่ม 1 ตุลาคม สิ้นสุด 30 กันยายน และโครงสร้างงบประมาณเปลี่ยนได้ทุกปีตามหลักเกณฑ์ของสำนักงบประมาณ
  • การเชื่อมต่อระบบภายนอกทำได้เฉพาะช่องทางที่หน่วยงานเจ้าของระบบอนุญาต ระหว่างรออนุญาตใช้การนำเข้า/ส่งออกไฟล์
  • ระบบไม่แทนที่ระบบบัญชีภาครัฐ ข้อมูลการเบิกจ่ายเป็นการนำเข้าเพื่อติดตามเท่านั้น
  • รูปแบบการติดตั้ง (Government Cloud, Private Cloud หรือ On-Premise) เป็นการตัดสินใจของหน่วยงาน ระบบออกแบบให้รองรับทั้งสามแบบ
  • AI ทำงานบนข้อมูลที่ได้รับอนุญาตและไม่ส่งข้อมูลออกนอกขอบเขตที่หน่วยงานกำหนด

3.3ความสามารถของ Workflow

ความสามารถรายละเอียด
Multi-Level Approvalกำหนดลำดับขั้นอนุมัติตามโครงสร้างหน่วยงาน และตามเงื่อนไข เช่น วงเงินหรือประเภทงบรายจ่าย
Delegation of Authorityมอบอำนาจชั่วคราวพร้อมช่วงวันที่และขอบเขต ระบบบันทึกผู้มอบและผู้รับมอบทุกครั้ง
Return for Revisionส่งกลับไปขั้นใดก็ได้ก่อนหน้าพร้อมความเห็น ผู้จัดทำเห็นจุดที่ต้องแก้
Version Controlทุกการส่งหรือปรับวงเงินสร้างเวอร์ชันใหม่ เปรียบเทียบเวอร์ชันได้
Deadline Managementกำหนดเส้นตายตามปฏิทินงบประมาณ แจ้งเตือนก่อนครบกำหนดและเมื่อเลยกำหนด
Notificationsแจ้งเตือนในระบบและอีเมล ตามบทบาทและเหตุการณ์
Audit Trailบันทึกผู้ดำเนินการ เวลา การกระทำ ค่าก่อนและหลังเปลี่ยน แก้ไขไม่ได้

04การออกแบบเชิงฟังก์ชัน

4.1M01 · Strategic Planning

รหัสข้อกำหนดความสำคัญ
FR-M01-01จัดทำแผนยุทธศาสตร์หน่วยงาน และแผนปฏิบัติราชการระยะ 5 ปีและรายปีMust
FR-M01-02กำหนดเป้าประสงค์ ตัวชี้วัด ค่าเป้าหมายรายปี และหน่วยวัดMust
FR-M01-03เชื่อมโยงกับยุทธศาสตร์ชาติและแผนระดับต่าง ๆ แบบหลายต่อหลายMust
FR-M01-04จัดโครงสร้างแผนงาน ผลผลิต/โครงการ กิจกรรม พร้อมหน่วยงานเจ้าของและผู้รับผิดชอบMust
FR-M01-05รายงานความสอดคล้องระหว่างแผนกับคำขอ (คำขอที่ไม่ผูกแผน แผนที่ไม่มีคำขอ)Should

4.2M02 · Budget Preparation

รหัสข้อกำหนดความสำคัญ
FR-M02-01สร้างคำขอรายโครงการ/กิจกรรม ภายใต้โครงสร้างงบประมาณของปีที่เปิดรับMust
FR-M02-02บันทึกรายการตามงบรายจ่าย (บุคลากร ดำเนินงาน ลงทุน เงินอุดหนุน รายจ่ายอื่น) หมวด และรายการMust
FR-M02-03คำนวณวงเงินอัตโนมัติ (จำนวน × ราคาต่อหน่วย) และสรุปตามงบรายจ่ายMust
FR-M02-04รองรับคำขอผูกพันต่อเนื่องหลายปี พร้อมวงเงินรายปีMust
FR-M02-05บันทึกเหตุผลความจำเป็น ตัวชี้วัด ผลผลิต ผลลัพธ์ และแนบเอกสารประกอบMust
FR-M02-06รายละเอียดครุภัณฑ์และสิ่งก่อสร้าง ตามแบบฟอร์มที่กำหนดMust
FR-M02-07ตรวจความครบถ้วนก่อนส่งตามกฎที่ตั้งค่าได้ แยกข้อผิดพลาดที่ส่งไม่ได้กับข้อสังเกตMust
FR-M02-08เปรียบเทียบกับงบประมาณที่ได้รับและคำขอปีก่อนShould
FR-M02-09ประมาณการงบบุคลากรจากข้อมูลอัตรากำลังที่นำเข้าShould

  • Fiscal-year scoped structure: โครงสร้างงบประมาณเป็นชุดของแต่ละปี การเปลี่ยนปีใหม่ไม่แก้ไขชุดเดิม
  • Versioned amounts: วงเงินทุกรอบเก็บแบบเพิ่มอย่างเดียว ไม่มีการ UPDATE ทับ
  • Effective-dated master data: หน่วยงานและข้อมูลหลักมีช่วงเวลาที่มีผล รายงานย้อนหลังแสดงตามโครงสร้าง ณ เวลานั้น
  • Cross-year mapping: ตารางจับคู่รหัสข้ามปีเพื่อเปรียบเทียบงบประมาณหลายปี

8.2รูปแบบและหลักการเชื่อมต่อ

  • API-First: บริการภายในทุกตัวเปิด API ที่มีเอกสาร (OpenAPI) และกำหนดเวอร์ชัน
  • Adapter ต่อระบบ: แต่ละระบบภายนอกมี Adapter แยก เปลี่ยนจากไฟล์เป็น API ได้โดยไม่กระทบโมดูลงาน
  • Staging ก่อนนำเข้า: ข้อมูลนำเข้าลงพื้นที่พักก่อน ตรวจรูปแบบ รหัส และยอดรวม แล้วจึงบันทึกจริง
  • Idempotent: นำเข้าซ้ำงวดเดิมได้โดยไม่เกิดข้อมูลซ้ำ
  • กระทบยอด: ทุกงวดเทียบยอดรวมกับแหล่งข้อมูล ส่วนต่างแสดงในรายงานให้ผู้รับผิดชอบตรวจ
  • จัดการข้อผิดพลาด: ลองใหม่อัตโนมัติตามรอบ บันทึกข้อผิดพลาด และแจ้งผู้ดูแลเมื่อเกินเกณฑ์
  • ความปลอดภัย: TLS 1.2 ขึ้นไป, Mutual TLS หรือ OAuth 2.0 Client Credentials, จำกัด IP, ไฟล์เข้ารหัสระหว่างส่ง

10การออกแบบความมั่นคงปลอดภัย

ออกแบบตามหลัก Defense in Depth และ Least Privilege สอดคล้องกฎหมายคุ้มครองข้อมูลส่วนบุคคลและกฎหมายการรักษาความมั่นคงปลอดภัยไซเบอร์

10.1การยืนยันตัวตนและการเข้าถึง

  • Single Sign-On กับ Identity Provider ของหน่วยงาน (SAML 2.0 / OpenID Connect)
  • Multi-Factor Authentication บังคับสำหรับผู้บริหาร กองแผนงาน การเงิน และผู้ดูแลระบบ
  • Role-Based Access Control ผสานกับขอบเขตหน่วยงาน (ผู้ใช้เห็นเฉพาะข้อมูลของหน่วยงานตนและหน่วยงานใต้สังกัด)
  • Session timeout เมื่อไม่ใช้งาน 30 นาที และยุติ Session เมื่อเปลี่ยนสิทธิ์
  • บัญชีสิทธิ์สูงตรวจทานทุกไตรมาส และแยกหน้าที่ผู้ดูแลระบบกับผู้ใช้งานธุรกิจ

10.3การปกป้องข้อมูล

ชั้นความลับ (เสนอ)ตัวอย่างมาตรการ
ลับวงเงินระหว่างพิจารณา มติคณะกรรมการ ข้อมูลเงินเดือนรายบุคคลจำกัดตามบทบาท ปกปิดใน UAT ไม่ส่งให้ AI แบบรายบุคคล
ใช้ภายในคำขอ แผนการใช้จ่าย ผลเบิกจ่ายRBAC + ขอบเขตหน่วยงาน
เปิดเผยได้งบประมาณที่ได้รับตามพระราชบัญญัติ ผลสัมฤทธิ์ที่เผยแพร่เผยแพร่ได้หลังอนุมัติ
  • เข้ารหัสระหว่างส่งด้วย TLS 1.2 ขึ้นไป และเข้ารหัสขณะจัดเก็บ (ฐานข้อมูล ไฟล์ สำรองข้อมูล) ด้วย AES-256
  • บริหารกุญแจผ่าน Key Management Service หรือ HSM ตามรูปแบบการติดตั้ง
  • Secrets ไม่อยู่ในโค้ดหรือไฟล์ตั้งค่า

10.4Audit และการตรวจจับ

  • บันทึกการเข้าสู่ระบบ การเปลี่ยนสิทธิ์ การสร้าง แก้ไข ส่ง อนุมัติ ส่งกลับ ปรับวงเงิน ส่งออกข้อมูล และการใช้ AI
  • Audit Log จัดเก็บแบบเพิ่มอย่างเดียวและตรวจความครบถ้วนได้ ส่งต่อไปยัง SIEM ของหน่วยงาน
  • แจ้งเตือนเหตุผิดปกติ เช่น เข้าสู่ระบบล้มเหลวต่อเนื่อง ส่งออกข้อมูลจำนวนมาก เข้าถึงนอกเวลาทำการ

10.5การคุ้มครองข้อมูลส่วนบุคคล

  • ใช้ข้อมูลส่วนบุคคลเท่าที่จำเป็น เช่น ข้อมูลผู้ใช้และอัตรากำลังเพื่อประมาณการงบบุคลากร
  • จัดทำบันทึกรายการกิจกรรมการประมวลผล (ROPA) และประเมินผลกระทบ (DPIA) สำหรับการใช้ AI และข้อมูล HR
  • ปกปิดข้อมูลในสภาพแวดล้อมทดสอบ
  • รองรับการใช้สิทธิ์ของเจ้าของข้อมูลตามกระบวนการของหน่วยงาน

10.6Secure Development และการทดสอบ

  • พัฒนาตามแนวทาง OWASP ASVS ระดับ 2 และตรวจ OWASP Top 10
  • Static/Dependency scanning ในทุก build, Dynamic scanning ก่อนขึ้น UAT
  • Penetration Test โดยผู้ทดสอบอิสระก่อน Go-Live และทุกปี
  • ทดสอบ Prompt Injection และการเข้าถึงข้อมูลข้ามสิทธิ์ของ AI ก่อนเปิดใช้
