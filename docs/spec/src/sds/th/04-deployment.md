# การติดตั้งและปรับใช้ {#deployment}

> [!NOTE] บทนี้ออกแบบการติดตั้งตาม ADR-0012 ตัวเลขการกู้คืน ตารางเวลา และระยะเก็บทั้งหมดในบทนี้เป็นข้อเสนอ ADR-0012 ให้ SRS เป็นผู้กำหนดเป้าหมายการกู้คืน ซึ่งเสนอ RPO 15 นาที และ RTO 4 ชั่วโมงต่อเซลล์ (XC-AVL-002, XC-AVL-003) เจ้าของผลิตภัณฑ์ต้องยืนยัน (OI-XC-02)

## ชุดติดตั้งที่รองรับ {#dep-setups}

สองชุดติดตั้งใช้ codebase เดียว และทดสอบทั้งคู่ในทุกรุ่น (ADR-0012) บริการแบบโฮสต์คือชุดองค์กรที่ผู้ให้บริการดำเนินการบนคลาวด์เชิงพาณิชย์ในไทย

| ส่วน | บริการแบบโฮสต์ | องค์กรติดตั้งเอง | ขนาดเล็กติดตั้งเอง |
| --- | --- | --- | --- |
| รันบน | Kubernetes แบบบริหารจัดการ สามโซน | Kubernetes แบบ high availability | Docker Compose |
| ฐานข้อมูล | PostgreSQL แบบบริหารจัดการ | คลัสเตอร์ PostgreSQL | PostgreSQL ตัวเดียว |
| กุญแจ | KMS ของคลาวด์ | OpenBao หรือ HSM | OpenBao |
| ไฟล์ | ที่เก็บวัตถุของคลาวด์ | Ceph RGW | ผลิตภัณฑ์ที่เข้ากันได้กับ S3 ใดก็ได้ |
| การส่งข้อความ | RabbitMQ | RabbitMQ | outbox อย่างเดียว |
| การค้นหา | OpenSearch | OpenSearch | การค้นหาของ PostgreSQL ผลภาษาไทยด้อยกว่า |
| เซลล์ | หลายเซลล์ | หนึ่งเซลล์ขึ้นไป | หนึ่งเซลล์ |
| การใช้งานที่ตั้งใจ | บริการที่ขายให้หน่วยงาน | หน่วยงานขนาดใหญ่ หรือ GDCC | การทดลองและหน่วยงานขนาดเล็ก |

## บริการแบบโฮสต์ {#dep-hosted}

บริการแบบโฮสต์รันบนคลาวด์เชิงพาณิชย์ในไทย ค่าเริ่มต้นคือ AWS Thailand (`ap-southeast-7`, สาม Availability Zone) โดยขึ้นกับว่ามีบริการแบบบริหารจัดการที่ต้องใช้ในภูมิภาคนั้น (ADR-0012)

{{fig:dep-hosted | การติดตั้งบริการแบบโฮสต์}}

- PostgreSQL, Kubernetes, ที่เก็บวัตถุ และ KMS แบบบริหารจัดการรันข้ามสามโซน
- ข้อเสนอนี้ให้แต่ละเซลล์มีคลัสเตอร์ Kubernetes ของตนเอง เพื่อให้การอัปเกรดคลัสเตอร์กระทบเพียงเซลล์เดียว ค่าใช้จ่ายของทางเลือกนี้บันทึกใน DG-XC-13
- โค้ดแอปใช้ส่วนเชื่อมต่อแบบเปิดเท่านั้น ส่วนเฉพาะคลาวด์อยู่ในโมดูล OpenTofu และค่า Helm
- ข้อมูล สำรองข้อมูล และบันทึกทั้งหมดอยู่ในไทย
- ปิดทราฟฟิกขาออกเป็นค่าเริ่มต้น แต่ละ adapter มีรายการปลายทางระบุชื่อ

> [!OPEN] บล็อกของผู้ขายรายหนึ่งระบุว่าการซื้อคลาวด์ของหน่วยงานต้องผ่าน GDCC หากเป็นจริง หน่วยงานอาจสมัครใช้บริการบนคลาวด์เชิงพาณิชย์ไม่ได้ DGA หรือ NT ต้องยืนยัน (ADR-0012, DG-XC-11) แผนสำรองคือติดตั้งเองบน GDCC

> [!OPEN] ผู้ให้บริการคลาวด์ต้องยืนยันว่ามีบริการแบบบริหารจัดการใดในภูมิภาคที่เลือก (ADR-0012, DG-XC-12) ช่องว่างใดจะเติมโดยรันผลิตภัณฑ์โอเพนซอร์สในคลัสเตอร์ ซึ่งเพิ่มงานปฏิบัติการ

## ชุดติดตั้งขนาดเล็ก {#dep-small}

ชุดติดตั้งขนาดเล็กรันบนโฮสต์เดียวด้วย Docker Compose สำหรับการทดลองและหน่วยงานขนาดเล็ก (ADR-0012)

{{fig:dep-small | การติดตั้งขนาดเล็กด้วย Docker Compose}}

- แอปรัน relay ของ outbox เอง โดยไม่มี RabbitMQ (ADR-0008)
- การค้นหาของ PostgreSQL แทน OpenSearch ผ่านส่วนเชื่อมต่อการค้นหา (ADR-0009)
- OpenBao เก็บกุญแจ และออกใบรับรองสำหรับ mutual TLS ระหว่างคอนเทนเนอร์ด้วย (ข้อเสนอ)
- ไฟล์ compose แม่แบบ environment และสคริปต์เริ่มต้นครั้งแรกมาพร้อมทุกรุ่น
- โฮสต์เดียวไม่มี high availability หน่วยงานที่เลือกชุดนี้ยอมรับข้อจำกัดดังกล่าว และสำรองข้อมูลต้องออกจากโฮสต์

## สภาพแวดล้อม {#dep-environments}

| สภาพแวดล้อม | วัตถุประสงค์ | ข้อมูล | การนำไปใช้ |
| --- | --- | --- | --- |
| Local | งานของนักพัฒนา Testcontainers | ข้อมูลสังเคราะห์ | โดยนักพัฒนา |
| CI | ทุก pull request และทุก merge | ข้อมูลสังเคราะห์ | โดย pipeline |
| Test | การเชื่อมโยงกับ adapter จำลอง | ข้อมูลสังเคราะห์ | เมื่อ merge เข้าสาขาหลัก |
| Staging | รุ่นทดสอบก่อนปล่อยบนเซลล์เล็กหนึ่งเซลล์ ทั้งสองชุดติดตั้ง และ load test | ข้อมูลสังเคราะห์ที่ปริมาณช่วงสูงสุด | เมื่อมี release candidate |
| Production | บริการแบบโฮสต์ | ข้อมูลผู้เช่า | ทีละเซลล์ |

ข้อมูลผู้เช่าไม่ออกจาก production และไม่ถูกคัดลอกไปสภาพแวดล้อมระดับล่าง ข้อมูลตัวอย่างของหน่วยงานไม่อยู่ใน image ใด adapter จำลองมีเฉพาะในโปรไฟล์ทดสอบ (PRC-NFR-006) รายการสภาพแวดล้อมนี้เป็นข้อเสนอ

## การสร้างเซลล์ {#dep-provisioning}

เซลล์ใหม่สร้างจากโค้ดโดยไม่มีขั้นตอนมือ เพื่อให้การรับหน่วยงานใหม่เป็นอัตโนมัติทั้งหมด (ADR-0005)

1. ผู้ปฏิบัติการเพิ่มเซลล์ในรายการของ control plane ผ่านการเปลี่ยนแปลงใน Git ที่ได้รับการทบทวน
2. OpenTofu สร้างคลัสเตอร์ ฐานข้อมูล ที่เก็บไฟล์ เครือข่าย และสิทธิ์ใช้กุญแจ
3. Argo CD นำ Helm release ของรุ่นปัจจุบันไปใช้กับเซลล์
4. control plane รัน smoke test แล้วเปิดเซลล์

### การรับหน่วยงานใหม่ {#dep-onboarding}

1. control plane สร้างระเบียนผู้เช่าและเลือกเซลล์
2. สร้าง Keycloak Organization และเชื่อมผู้ให้บริการตัวตนของหน่วยงาน
3. สร้าง keyset ของผู้เช่า ห่อด้วยกุญแจหลัก
4. เพิ่มผู้เช่าในแผนที่ส่งต่อ
5. โหลดค่าตั้งเริ่มต้นภายในช่วงที่อนุญาต และแม่แบบในฐานะข้อมูลของผู้เช่า
6. รัน smoke test ของผู้เช่าและเขียนรายการ Audit แรก

### การย้ายผู้เช่า {#dep-move}

การย้ายผู้เช่าระหว่างเซลล์เป็นการดำเนินการที่รองรับ (ADR-0005)

1. คัดลอกแถวและไฟล์ของผู้เช่าไปเซลล์ปลายทางขณะที่ผู้เช่ายังทำงาน
2. ตั้งผู้เช่าเป็นโหมดบำรุงรักษา และรอจน outbox ของผู้เช่าว่าง
3. คัดลอกการเปลี่ยนแปลงล่าสุด แล้วตรวจจำนวนแถวและลูกโซ่ Audit เทียบกับจุดตรวจ
4. เปลี่ยนแผนที่ส่งต่อ สร้างดัชนีค้นหาใหม่ และเปิดผู้เช่า
5. เก็บแถวต้นทางไว้ตามระยะที่กำหนด แล้วจึงลบ

## การสำรองและกู้คืน {#dep-backup}

สำรองข้อมูลอยู่ในไทยและเข้ารหัส (ADR-0012, ADR-0013) ตารางเวลาและระยะเก็บด้านล่างเป็นข้อเสนอ

| สิ่งที่สำรอง | วิธี | ความถี่ | เก็บนาน |
| --- | --- | --- | --- |
| PostgreSQL | archive ต่อเนื่องพร้อม point-in-time recovery | ต่อเนื่อง และ base backup รายวัน | 35 วัน |
| PostgreSQL ระยะยาว | สำเนารายเดือน | รายเดือน | ตามตารางระยะเก็บ (DG-XC-05) |
| ที่เก็บวัตถุ | versioning และสำเนาไปตำแหน่งที่สอง | ต่อเนื่อง | 35 วันหลังการลบ |
| จุดตรวจ Audit | ที่เก็บวัตถุแบบเขียนครั้งเดียว | ทุกจุดตรวจ | ตามตารางระยะเก็บ |
| ฐานข้อมูลของ Keycloak และ control plane | เช่นเดียวกับ PostgreSQL | ต่อเนื่อง | 35 วัน |
| keyset ที่ห่อแล้ว | อยู่ในสำรองของฐานข้อมูล | พร้อมฐานข้อมูล | พร้อมฐานข้อมูล |
| กุญแจหลัก | เก็บใน KMS หรือ recovery share ของ OpenBao สำหรับผู้ติดตั้งเอง | เมื่อเปลี่ยน | ตลอดอายุข้อมูล |
| ดัชนีค้นหา | ไม่สำรอง สร้างใหม่จาก PostgreSQL | ไม่เกี่ยวข้อง | ไม่เกี่ยวข้อง |

### การส่งออกและกู้คืนรายผู้เช่า {#dep-tenant-restore}

การส่งออกและกู้คืนรายผู้เช่าสร้างตั้งแต่ต้น เพื่อให้การกู้คืนหน่วยงานเดียวไม่ต้องย้อนฐานข้อมูลทั้งชุด (ADR-0005)

{{fig:dep-tenant-restore | การกู้คืนรายหน่วยงาน}}

- เครื่องมือเป็นตัวเดียวกับที่ใช้ย้ายผู้เช่า จึงถูกใช้บ่อยและคงความถูกต้อง
- การส่งออกมีแถวของผู้เช่า ไฟล์ และ manifest ที่ลงนาม เข้ารหัสด้วยกุญแจของผู้เช่า
- หลังการกู้คืน ระบบทำตามรายการลบซ้ำก่อนเปิดผู้เช่า (ดูส่วน Audit log ในบทการออกแบบส่วนกลาง)
- การส่งออกของผู้เช่ายังเป็นวิธีที่หน่วยงานใช้เมื่อเลิกใช้บริการ

### การซ้อม {#dep-rehearsal}

เป้าหมายการกู้คืนต้องมีการซ้อม (ADR-0012) ข้อเสนอคือซ้อมกู้คืนอย่างน้อยทุก 90 วันบน staging ครอบคลุมทั้งเซลล์และผู้เช่าหนึ่งราย และซ้อมกู้กุญแจอย่างน้อยทุก 12 เดือน พร้อมบันทึกผลและเวลาที่วัดได้ และระบบแสดงวันที่ทดสอบกู้คืนล่าสุด (XC-AVL-009, XC-SEC-031)

## การกู้คืนจากภัยพิบัติ {#dep-dr}

ตัวเลขด้านล่างเป็นข้อเสนอให้เจ้าของผลิตภัณฑ์ยืนยัน RPO คือปริมาณข้อมูลที่อาจสูญเสียได้มากที่สุด RTO คือเวลานานที่สุดในการกลับมาให้บริการ

| เหตุการณ์ | การตอบสนอง | RPO (ข้อเสนอ) | RTO (ข้อเสนอ) |
| --- | --- | --- | --- |
| อินสแตนซ์หรือ node หนึ่งล้มเหลว | เริ่มใหม่อัตโนมัติ | 0 | 5 นาที |
| หนึ่งโซนล้มเหลว | ตัวสำรองรับช่วง ทราฟฟิกย้าย และบริการดำเนินต่อ (XC-AVL-004) | 0 | 15 นาที |
| เซลล์ล้มเหลว หรือฐานข้อมูลของเซลล์เสียหาย | point-in-time recovery ไปคลัสเตอร์ใหม่ (XC-AVL-002, XC-AVL-003) | 15 นาที | 4 ชั่วโมง |
| ข้อมูลของผู้เช่าหนึ่งรายเสียหาย | การกู้คืนรายผู้เช่า (XC-AVL-008) | 15 นาที | 8 ชั่วโมง |
| บริการระดับรวมล้มเหลว | ติดตั้งใหม่จากโค้ด และกู้ฐานข้อมูลของบริการ | 15 นาที | 4 ชั่วโมง |
| สูญเสียทั้งภูมิภาค | สร้างใหม่ที่ไซต์ที่สองในไทยจากสำเนานอกสถานที่ | 24 ชั่วโมง | 72 ชั่วโมง |

> [!OPEN] ADR-0012 กำหนดให้ข้อมูลทั้งหมดอยู่ในไทย และการออกแบบนี้สมมติว่าคลาวด์ที่เลือกมีภูมิภาคเดียวในไทย ไซต์ที่สองจึงต้องเป็นผู้ให้บริการอื่น GDCC หรือศูนย์ข้อมูลในไทย เจ้าของผลิตภัณฑ์ต้องตัดสินเรื่องไซต์และการให้คำมั่นเป้าหมายกรณีสูญเสียภูมิภาคแก่หน่วยงาน หลังผู้ให้บริการคลาวด์ยืนยันภูมิภาคแล้ว (DG-XC-14)

## การอัปเกรดทีละเซลล์ {#dep-upgrades}

การเปลี่ยน schema ใช้แนวทาง expand และ contract เพื่อให้แอปรุ่นเก่าและใหม่ทำงานร่วมกันได้ระหว่าง rolling upgrade (ADR-0005) การอัปเกรดทยอยทีละเซลล์

{{fig:dep-rollout | การอัปเกรดทีละเซลล์}}

- นำไปใช้เฉพาะรุ่นที่ลงนามแล้ว และ Argo CD ตรวจลายเซ็นก่อน
- รุ่นใหม่ต้องทำงานกับ schema ของรุ่นก่อน และรุ่นก่อนต้องทำงานได้หลังขั้น expand ช่วงความเข้ากันได้คือหนึ่งรุ่น
- ขั้น contract มาในรุ่นถัดไป เมื่อทุกเซลล์ผ่านขั้น expand แล้ว
- การถอยกลับเปลี่ยนเฉพาะแอป schema ยังคงขยายอยู่
- ผู้เช่าแต่ละรายมีรุ่นเดียวในแต่ละเวลา ผู้เช่าต่างเซลล์อาจต่างกันหนึ่งรุ่นระหว่างการปล่อย API และเหตุการณ์จึงต้องเข้ากันได้ในช่วงนั้น
- การเปลี่ยนกฎตามกฎหมายใช้รุ่นกฎตามวันที่ จึงมีผลตามวันที่ในทุกเซลล์ และแฟ้มเก่าคงใช้กฎเดิม (ADR-0007)
- ไม่ปล่อยรุ่นหลักและไม่มีการบำรุงรักษาตามแผนตั้งแต่ 15 กันยายนถึง 5 ตุลาคม (XC-AVL-007, ข้อเสนอ) การบำรุงรักษาตามแผนต้องประกาศล่วงหน้าอย่างน้อย 5 วันทำการ

## แผนการติดตั้ง {#dep-plan}

แผนนี้เรียงลำดับงานและระบุสิ่งที่ต้องเป็นจริงก่อนไปขั้นถัดไป ไม่มีวันที่ เพราะเจ้าของผลิตภัณฑ์ยังไม่ได้กำหนด

| ระยะ | งาน | เงื่อนไขการผ่าน |
| --- | --- | --- |
| ยืนยัน | คำถาม GDCC บริการในภูมิภาค การตรวจใบอนุญาต เงื่อนไข ThaID | ข้อเท็จจริงทุกข้อในดัชนี ADR ได้คำตอบ หรือเลือกแผนสำรองแล้ว |
| รากฐาน | OpenTofu, Helm, Argo CD, CI pipeline, บริการระดับรวม, เซลล์ staging หนึ่งเซลล์ | รุ่นที่ลงนามถึง staging โดยไม่มีขั้นตอนมือ |
| นำร่อง | เซลล์ร่วมหนึ่งเซลล์ หน่วยงานกลุ่มแรก | ผ่านการซ้อมกู้คืน และบรรลุวัตถุประสงค์ครบหนึ่งเดือนเต็ม |
| ขยาย | เซลล์ตามความหนาแน่นที่ทดสอบแล้ว load test ช่วงสูงสุด | k6 ผ่านช่วงสูงสุดวันที่ 30 กันยายน และ Keycloak ผ่านที่เป้าหมาย 500 ผู้เช่า |
| ติดตั้งเอง | ชุดขนาดเล็กและองค์กร เอกสาร | ทั้งสองชุดผ่านในรุ่นนั้น และบุคคลภายนอกติดตั้งได้จากเอกสาร |
| ดำเนินงาน | ปล่อยรุ่นต่อเนื่อง ซ้อมกู้คืน ทดสอบเจาะระบบก่อนรุ่นหลักทุกรุ่น | ต่อเนื่อง |
