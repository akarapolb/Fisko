# สถาปัตยกรรม {#architecture}

> [!NOTE] Fisko ยังไม่มีโค้ดสำหรับใช้งานจริง บทนี้นำการตัดสินใจที่ยอมรับแล้วใน `docs/adr/` มาใช้และไม่เปิดประเด็นใหม่ ส่วนใดที่ลงรายละเอียดเกินกว่า ADR จะระบุไว้ และส่วนนั้นเป็นข้อเสนอเพื่อการสร้าง

## ปัจจัยขับเคลื่อน {#arch-drivers}

ข้อเท็จจริงต่อไปนี้กำหนดรูปแบบของสถาปัตยกรรม แต่ละข้อมาจาก ADR

| ปัจจัย | ที่มา | ผลต่อการออกแบบ |
| --- | --- | --- |
| คาดว่าจะมีประมาณ 500 หน่วยงานภายใน 2 ถึง 3 ปี | ADR-0005 | จัดกลุ่มผู้เช่าเป็นเซลล์ และการรับหน่วยงานใหม่เป็นอัตโนมัติทั้งหมด |
| ทุกหน่วยงานมีปริมาณงานสูงสุดพร้อมกันเมื่อสิ้นปีงบประมาณวันที่ 30 กันยายน | ADR-0005 | วางแผนความจุตามช่วงสูงสุดนั้น ไม่ใช่วันปกติ |
| การกระทำจำนวนมากข้ามโมดูลในธุรกรรมเดียว | ADR-0002 | แอปพลิเคชันเดียว และฐานข้อมูลหนึ่งชุดต่อเซลล์ |
| ทีมพัฒนา 10 คนขึ้นไปถนัด Java และ Kotlin มากที่สุด | ADR-0002, ADR-0003 | Java และ Spring Boot พร้อมขอบเขตโมดูลที่บังคับใช้ |
| ขั้นตอนตามกฎหมายเปลี่ยนไม่บ่อยและเปลี่ยนตามกฎหมายเท่านั้น | ADR-0007 | workflow ตามกฎหมายอยู่ในโค้ด พร้อมรุ่นกฎตามวันที่ |
| ฐานข้อมูลเดียวอาจเก็บเลขประจำตัวประชาชน บัญชีธนาคาร และซองเสนอราคาของหลายหน่วยงาน | ADR-0013 | เข้ารหัสระดับฟิลด์ด้วยกุญแจรายผู้เช่า |
| การตรวจสอบภาครัฐต้องการบันทึกที่แก้ไขโดยไม่มีผู้รู้ไม่ได้ | ADR-0015 | Audit log แบบลูกโซ่แฮชที่ไม่มีข้อมูลส่วนบุคคล |
| ผลิตภัณฑ์เป็นโอเพนซอร์ส และหน่วยงานอาจติดตั้งเอง | ADR-0001, ADR-0012 | ใช้ส่วนเชื่อมต่อแบบเปิดเท่านั้น และมีสองชุดติดตั้งที่รองรับ |
| ความน่าเชื่อถือและคุณภาพต้องวัดได้ | ADR-0017 | OpenTelemetry และการทดสอบที่เชื่อมกับข้อกำหนด |

## ข้อจำกัด {#arch-constraints}

| ข้อจำกัด | ที่มา |
| --- | --- |
| ข้อมูล สำรองข้อมูล บันทึก และเครื่องมือสนับสนุนทั้งหมดอยู่ในประเทศไทย | ADR-0012, ADR-0014 |
| dependency ทุกตัวต้องเข้ากันได้กับ AGPL-3.0 | ADR-0001 |
| โค้ดแอปพลิเคชันใช้ส่วนเชื่อมต่อแบบเปิดเท่านั้น เพื่อย้ายไป GDCC หรือศูนย์ข้อมูลของหน่วยงานได้ | ADR-0012 |
| ไม่มีชื่อหน่วยงานในโค้ด ความแตกต่างเป็นค่าตั้งของผู้เช่าภายในช่วงที่อนุญาต | ADR-0004, ADR-0007 |
| AI ปิดเป็นค่าเริ่มต้น และทุกคุณสมบัติทำงานได้โดยไม่มี AI | ADR-0016 |
| จำนวนเงินใช้ `BigDecimal` เท่านั้น | ADR-0003 |
| ขั้นตอนจัดซื้อจัดจ้างอย่างเป็นทางการอยู่ใน e-GP | PRC-CR-001 |

> [!WARN] การออกแบบแบบโฮสต์ตั้งอยู่บนข้อเท็จจริงที่ยังไม่ยืนยัน คือหน่วยงานซื้อบริการบนคลาวด์เชิงพาณิชย์ได้หรือไม่ (ADR-0012) แผนสำรองคือติดตั้งเองบน GDCC ซึ่งกฎส่วนเชื่อมต่อแบบเปิดทำให้เป็นไปได้ บทการติดตั้งและปรับใช้บันทึกการตัดสินใจที่ต้องมี

## มุมมองบริบท {#arch-context}

Fisko อยู่ระหว่างผู้ใช้จากหน่วยงานและผู้ขายด้านหนึ่ง กับระบบของรัฐอีกด้านหนึ่ง

{{fig:arch-context | บริบทของระบบ Fisko}}

| ระบบภายนอก | วัตถุประสงค์ | การตัดสินใจ |
| --- | --- | --- |
| ThaID และไดเรกทอรีของหน่วยงาน | การเข้าสู่ระบบ | ADR-0006 |
| GFMIS | รายการการเงินภาครัฐ | ADR-0008 |
| e-GP | ข้อมูลการจัดซื้อจัดจ้างภาครัฐ | ADR-0008 |
| อีเมล และ SMS หาก OI-PLT-14 อนุญาต | การแจ้งเตือนถึงเจ้าหน้าที่และผู้ขาย | ADR-0002 |
| ผู้ให้บริการ AI | ผู้ช่วยที่เลือกใช้ได้ ปิดเป็นค่าเริ่มต้น | ADR-0016 |

> [!OPEN] ยังไม่ได้รับการยืนยันว่า GFMIS และ e-GP เชื่อมต่ออย่างไร กรมบัญชีกลางต้องให้รายละเอียดส่วนเชื่อมต่อ

## มุมมองคอนเทนเนอร์ {#arch-container}

เบราว์เซอร์เข้าถึง edge และ edge ส่งแต่ละคำขอไปยังเซลล์ของหน่วยงานของผู้ใช้ Keycloak, KMS, edge และ tenant router อยู่นอกเซลล์ ส่วนที่เก็บข้อมูลของผู้เช่าทั้งหมดอยู่ในเซลล์

{{fig:arch-container | คอนเทนเนอร์ของบริการแบบโฮสต์}}

| คอนเทนเนอร์ | รันบน | ขอบเขต | หน้าที่ | การตัดสินใจ |
| --- | --- | --- | --- | --- |
| Web client | React ในเบราว์เซอร์ | ให้บริการจาก edge | หน้าจอและการแปลภาษา ไม่มีกฎที่มีผลต่อความมั่นคงปลอดภัย | ADR-0004, ADR-0006 |
| Edge | Load balancer และ WAF ของคลาวด์ หรือ reverse proxy เมื่อติดตั้งเอง | ระดับรวม | TLS 1.3, WAF, จำกัดอัตรา, ไฟล์คงที่ | ADR-0012, ADR-0013 |
| Tenant router | บริการขนาดเล็กไร้สถานะ | ระดับรวม | จับคู่ผู้เช่ากับเซลล์ | ADR-0005 |
| Keycloak | Keycloak พร้อม Organizations | ระดับรวม | การเข้าสู่ระบบ, MFA, สหพันธ์ตัวตน | ADR-0006 |
| Control plane | บริการปฏิบัติการ | ระดับรวม | รับหน่วยงานใหม่ ย้ายผู้เช่า ส่งออกและกู้คืน ปล่อยรุ่น | ADR-0005 |
| KMS หรือ OpenBao | KMS ของคลาวด์, HSM หรือ OpenBao | ระดับรวม | กุญแจหลักและการบันทึกทุกการใช้กุญแจ | ADR-0013 |
| แอปพลิเคชัน Fisko | Spring Boot แบบ modular monolith | รายเซลล์ | โมดูลธุรกิจทั้งหมดและ REST API | ADR-0002, ADR-0003 |
| Relay และ worker | image เดียวกับแอป ต่างบทบาทของโปรเซส | รายเซลล์ | ส่งต่อ outbox งานตามกำหนดเวลา คิวสแกนไฟล์ | ADR-0008 |
| Adapter | image เดียวกัน บทบาท adapter | รายเซลล์ | เรียก GFMIS, e-GP, อีเมล และ SMS หาก OI-PLT-14 อนุญาต | ADR-0008 |
| PostgreSQL | คลัสเตอร์แบบบริหารจัดการหรือติดตั้งเอง | รายเซลล์ | แหล่งข้อมูลจริง, row-level security, outbox, Audit log | ADR-0005 |
| RabbitMQ | Broker | รายเซลล์ | ส่งเหตุการณ์ ไม่มีในชุดติดตั้งขนาดเล็ก | ADR-0008 |
| OpenSearch | คลัสเตอร์ค้นหา | รายเซลล์ | ค้นหาภาษาไทย สร้างดัชนีใหม่ได้ | ADR-0009 |
| ที่เก็บ S3 API และ ClamAV | ที่เก็บวัตถุและตัวสแกน | รายเซลล์ | ไฟล์ที่ผ่านการสแกนก่อนดาวน์โหลด | ADR-0010 |

> [!NOTE] ADR กำหนดให้แต่ละเซลล์มีคลัสเตอร์ฐานข้อมูลและอินสแตนซ์แอปของตนเอง หน้าสถาปัตยกรรมยังวาด RabbitMQ, OpenSearch และที่เก็บไฟล์ไว้ในเซลล์ด้วย การออกแบบนี้ยึดตามนั้น การใช้ image เดียวหลายบทบาทของโปรเซสเป็นข้อเสนอ ซึ่งทำให้การปฏิบัติการเรียบง่าย (ADR-0002) และขยายแต่ละบทบาทแยกกันได้

## โครงสร้างแบบโมดูล {#arch-modules}

Fisko เป็นแอปพลิเคชันเดียวที่แบ่งเป็นหกโมดูลของ Spring Modulith (ADR-0002) โมดูลเรียกกันผ่านส่วนเชื่อมต่อที่เผยแพร่และเหตุการณ์เท่านั้น และการทดสอบขอบเขตทำงานใน CI บทภาพรวมการออกแบบโมดูลอธิบายว่าแต่ละโมดูลสร้างอย่างไร

| โมดูล | เก็บอะไร | รายละเอียด |
| --- | --- | --- |
| `platform` | ผู้เช่า ตัวตน บทบาท การแยกหน้าที่ การมอบอำนาจ Audit การแจ้งเตือน PDPA | [บท Platform](#plt) |
| `budget` | รายการจัดสรรและบัญชีคุมงบ | [บท Budget](#bgt) |
| `procurement` | แผน แฟ้มจัดซื้อ สัญญา การตรวจรับ | [บท Procurement](#prc) |
| `finance` | ใบสำคัญ การจ่ายเงิน GFMIS | [บท Finance](#fin) |
| `projects` | โครงการ | [บท Projects](#prj) |
| `review` | การทบทวนและการวิเคราะห์ | [บท Review](#rev) |

โมดูลพึ่งพากันในทิศทางเดียว บทภาพรวมการออกแบบโมดูลแสดงทิศทางนั้นเป็นภาพและระบุการพึ่งพาแต่ละรายการ

## เส้นทางของคำขอ {#arch-request-path}

คำขอเว็บหนึ่งรายการทำงานหนึ่งคำสั่งในธุรกรรม PostgreSQL หนึ่งธุรกรรม ธุรกรรมนั้นบันทึก aggregate รายการ Audit และแถว outbox พร้อมกัน รายงานหรือการส่งออกที่คาดว่าเกิน 10 วินาทีจะทำเป็นงานเบื้องหลัง และแจ้งผู้ใช้เมื่อพร้อม (XC-PER-006)

{{fig:arch-request-path | เส้นทางของคำขอหนึ่งรายการ}}

| ขั้น | การควบคุม | เมื่อไม่ผ่าน |
| --- | --- | --- |
| Edge | TLS 1.3, WAF, จำกัดอัตรา | ปฏิเสธคำขอที่ edge |
| Tenant router | อ่าน claim ของ organization และหาเซลล์จากแผนที่ที่แคชไว้ | ไม่พบเซลล์ของผู้เช่า: 404 ผู้เช่าอยู่ระหว่างบำรุงรักษา: 503 พร้อม `Retry-After` |
| ตรวจโทเค็นในเซลล์ | แอปตรวจโทเค็นอีกครั้งและไม่เชื่อสิ่งใดจาก router | 401 |
| ผูกผู้เช่า | `SET LOCAL app.tenant_id` เป็นคำสั่งแรกของธุรกรรม | หากไม่ตั้งค่า ทุกคำสั่งบนตารางผู้เช่าจะล้มเหลว ความผิดพลาดจึงจบที่ข้อผิดพลาด ไม่ใช่ข้อมูลของผู้เช่าอื่น |
| สิทธิ์และหน้าที่ | `Authorizer` แล้ว `SodGuard` | 403 การปฏิเสธจากการแยกหน้าที่บันทึกในธุรกรรมแยก |
| คำสั่งธุรกิจ | เมธอดของโดเมนตรวจสถานะและกฎ | 409 หรือ 422 พร้อมรหัสคงที่ |
| Commit | aggregate รายการ Audit และแถว outbox บันทึกพร้อมกัน | ไม่มีสิ่งใดถูกบันทึก |
| หลัง commit | Relay เผยแพร่ ส่วน adapter การสร้างเอกสาร และการทำดัชนีทำงานจากเหตุการณ์ | แสดงสถานะให้ผู้ใช้เห็น และคำสั่งไม่ถูกย้อนกลับ |

Router อ่าน claim เพียงเพื่อเลือกเซลล์ การอนุญาตเกิดขึ้นในเซลล์ แผนที่ที่ผิดจึงอาจส่งคำขอไปผิดเซลล์ได้ แต่เปิดข้อมูลไม่ได้ เพราะไม่มีผู้เช่าของโทเค็นนั้นในเซลล์ดังกล่าว และคำขอจบที่ 404

## การสื่อสารด้วยเหตุการณ์ {#arch-events}

โมดูลและระบบภายนอกรับรู้เหตุการณ์ผ่าน transactional outbox (ADR-0008) เหตุการณ์ไม่สูญหาย และไม่ถูกส่งสำหรับธุรกรรมที่ย้อนกลับ

- schema ของแต่ละโมดูลมีตาราง `outbox_event` ซึ่งเขียนในธุรกรรมของการเปลี่ยนแปลง
- โปรเซส relay อ่านแถวที่ยังไม่ส่ง เผยแพร่ไป RabbitMQ รอการยืนยันจาก broker แล้วตั้ง `published_at` รันหลาย relay ได้ เพราะแต่ละแถวถูกจองด้วย `FOR UPDATE SKIP LOCKED`
- การส่งเป็นแบบอย่างน้อยหนึ่งครั้ง ผู้รับตัดรายการซ้ำด้วย `eventId`
- routing key ขึ้นต้นด้วยชื่อโมดูล เช่น `procurement.contract.signed` และ AsyncAPI อธิบายทุกเหตุการณ์
- payload เก็บการอ้างอิงและจำนวนเงิน ไม่มีข้อมูลส่วนบุคคล
- ชุดติดตั้งขนาดเล็กไม่มี RabbitMQ relay ตัวเดียวกันจะส่งเหตุการณ์ให้ส่วนเชื่อมต่อผู้รับเดียวกันภายในโปรเซส

การเรียกที่ต้องสำเร็จหรือล้มเหลวพร้อมการเปลี่ยนแปลงทางธุรกิจยังคงเป็นแบบทันที ผ่านส่วนเชื่อมต่อที่เผยแพร่ในธุรกรรมเดียวกัน การเรียก Budget เป็นตัวอย่างหลัก เหตุการณ์ใช้กับสิ่งที่เกิดขึ้นภายหลังได้

ลำดับจาก outbox ถึงระบบภายนอกอยู่ในบทการเชื่อมโยงระบบ

> [!NOTE] relay ต้องอ่านแถว outbox ของทุกผู้เช่าในเซลล์ จึงใช้บทบาทฐานข้อมูลของตนเองซึ่งมี policy จำกัดเฉพาะตาราง outbox และไม่อ่านตารางธุรกิจ

## สถาปัตยกรรมข้อมูล {#arch-data}

PostgreSQL เป็นแหล่งข้อมูลจริง ส่วน OpenSearch และ projection ทั้งหมดสร้างใหม่จากแหล่งนี้ได้ (ADR-0009)

### เซลล์ {#arch-cells}

ผู้เช่าถูกจัดกลุ่มเป็นเซลล์ แต่ละเซลล์มีคลัสเตอร์ฐานข้อมูลและอินสแตนซ์แอปของตนเอง (ADR-0005) ความล้มเหลวกระทบเซลล์เดียว และการอัปเกรดทยอยทีละเซลล์

{{fig:arch-cells | เซลล์และบริการระดับรวม}}

| รายการ | การออกแบบ | ที่มา |
| --- | --- | --- |
| เซลล์ร่วม | เริ่มที่ประมาณ 50 ถึง 100 หน่วยงานขนาดเล็ก และปรับจาก load test | ADR-0005 |
| จำนวนเซลล์ที่เป้าหมาย | 5 ถึง 10 เซลล์สำหรับ 500 หน่วยงานขนาดเล็กที่ความหนาแน่นดังกล่าว และมากขึ้นหากมีเซลล์เฉพาะ | คำนวณจาก ADR-0005 |
| เซลล์เฉพาะ | หน่วยงานขนาดใหญ่มีเซลล์ของตนเอง การแยกเป็นค่าตั้งและไม่ต้องแก้โค้ด | ADR-0005 |
| การย้ายผู้เช่า | เป็นการดำเนินการที่รองรับ อธิบายในบทการติดตั้งและปรับใช้ | ADR-0005 |
| การส่งต่อ | บริการส่งต่อระดับรวมจับคู่ผู้เช่ากับเซลล์ แผนที่เก็บรหัสผู้เช่า รหัสเซลล์ และสถานะ ไม่มีข้อมูลส่วนบุคคล | ADR-0005 |

### Row-level security {#arch-rls}

ทุกแถวของผู้เช่ามี `tenant_id` และเปิดใช้พร้อมบังคับ row-level security ทุกตารางดังกล่าว (ADR-0005) รูปแบบอยู่ในบท Procurement และ CI ทดสอบทุกตาราง บทการออกแบบส่วนกลางแสดงชั้นการบังคับใช้

### ข้อมูลอยู่ที่ใด {#arch-data-places}

| ข้อมูล | ที่เก็บ | ขอบเขต |
| --- | --- | --- |
| ระเบียนของโมดูล | PostgreSQL หนึ่ง schema ต่อโมดูล | เซลล์ |
| Audit log และตารางบุคคล | schema `platform` | เซลล์ |
| จุดตรวจ Audit | ที่เก็บวัตถุแบบเขียนครั้งเดียว แยกจากฐานข้อมูล | เซลล์ |
| ไฟล์ | ที่เก็บ S3 API เข้ารหัสด้วยกุญแจของผู้เช่า | เซลล์ |
| เอกสารค้นหา ไม่มีข้อมูล Restricted | OpenSearch | เซลล์ |
| แผนที่ผู้เช่าถึงเซลล์ รายการเซลล์ | ฐานข้อมูลของ control plane | ระดับรวม |
| บัญชีผู้ใช้และ organization | ฐานข้อมูลของ Keycloak | ระดับรวม |
| กุญแจหลัก | KMS, HSM หรือ OpenBao | ระดับรวม |

โมดูลอื่นไม่อ่านตารางของโมดูลหนึ่งโดยตรง แต่ใช้แพ็กเกจ `api` ของโมดูลนั้น การเปลี่ยน schema ใช้แนวทาง expand และ contract เพื่อให้แอปรุ่นเก่าและใหม่ทำงานร่วมกันได้ระหว่าง rolling upgrade (ADR-0005)

## ความพร้อมใช้งานสูงและการขยายขนาด {#arch-ha}

ตัวเลขความพร้อมใช้งานเป็นวัตถุประสงค์ของบริการ และเป็นข้อเสนอในบทการเฝ้าระวัง ส่วนนี้ระบุเฉพาะกลไก

| ส่วน | ความพร้อมใช้งาน | การขยายขนาด |
| --- | --- | --- |
| แอปพลิเคชัน | อินสแตนซ์ในสามโซน ไร้สถานะ มีการตรวจสุขภาพ | เพิ่มอินสแตนซ์ในเซลล์ แล้วจึงเพิ่มเซลล์ |
| PostgreSQL | ตัวหลักแบบบริหารจัดการพร้อมตัวสำรองข้ามโซน | เพิ่มขนาด ใช้ read replica สำหรับรายงาน แล้วจึงเพิ่มเซลล์ |
| RabbitMQ | คิวแบบจำลองข้ามโซน | เพิ่มผู้รับ งานค้างรออย่างปลอดภัยใน outbox |
| OpenSearch | สำเนาข้ามโซน | เพิ่ม data node และสร้างดัชนีใหม่ได้ |
| ที่เก็บวัตถุ | บริการคลาวด์ข้ามโซน | เติบโตตามการใช้งาน |
| Edge และ router | หลายอินสแตนซ์ข้ามโซน | เพิ่มอินสแตนซ์ เพราะ router ไร้สถานะ |
| Keycloak | คลัสเตอร์ข้ามโซน | load test ที่เป้าหมาย 500 ผู้เช่า (ADR-0006) |

วางแผนความจุตามช่วงสูงสุดวันที่ 30 กันยายน k6 ทดสอบช่วงนั้นก่อนรุ่นหลักทุกรุ่น (XC-TST-003) เซลล์ที่ใกล้ขีดจำกัดจะแบ่งโดยย้ายผู้เช่าไปเซลล์ใหม่โดยไม่แก้โค้ด

row lock ของบัญชีคุมงบ Budget คาดว่าเป็นจุดแย่งทรัพยากรในช่วงสูงสุด (ดูบท Procurement) load test ต้องวัดจุดนี้ก่อน
