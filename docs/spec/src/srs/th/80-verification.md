# การทวนสอบและการตรวจรับ {#verification}

บทนี้ระบุว่าจะพิสูจน์ข้อกำหนดแต่ละข้ออย่างไร ข้อกฎหมายโยงไปถึงการทดสอบอย่างไร และคอลัมน์สถานะหมายถึงอะไร ขณะนี้ยังไม่มีโค้ดสำหรับใช้งานจริง หลักฐานที่มีอยู่จึงมีเพียงต้นแบบและชุดทดสอบ sweep บทนี้แยกหลักฐานดังกล่าวออกจากการทดสอบระบบจริงที่ SDS วางแผนไว้

## ระดับการทดสอบ {#ver-levels}

แถวแรกมีอยู่แล้ว แถวอื่นเป็นแผนทั้งหมด เครื่องมือมาจาก ADR-0017 และหัวข้อการทดสอบในบทข้อกำหนดร่วม แต่ละบทโมดูลใน SDS ระบุการทดสอบของตนไว้ในหัวข้อการออกแบบการทดสอบ

| ระดับ | เครื่องมือ | สิ่งที่พิสูจน์ | ที่มา | สถานะ |
| --- | --- | --- | --- | --- |
| Sweep ของต้นแบบ | `tests/sweep.js`, `tests/run.html` | การเดินผ่านขั้นตอนที่สั่งงานจริงบนหน้าเว็บและแจ้งข้อผิดพลาดเมื่อผลลัพธ์ผิด และการเปิดทุกหน้าสำหรับทุกบทบาท ภาษา และหน่วยงานตัวอย่าง | XC-TST-002 | มีแล้ว แต่ไม่ได้รันสำหรับฉบับนี้ |
| หน่วย | JUnit | ตารางสถานะ ตัวคำนวณ และนโยบาย โดยไม่ใช้ Spring context | XC-TST-001 | วางแผน |
| สถาปัตยกรรม | Spring Modulith `verify`, ArchUnit | ขอบเขตโมดูล ไม่มีวงจร และไม่มี framework ในชั้น domain | XC-TST-006 | วางแผน |
| การรวมระบบ | JUnit, Testcontainers | คำสั่งผ่านชั้น REST, row-level security ทุกตารางของหน่วยงาน และ outbox | XC-TST-001, XC-TST-005 | วางแผน |
| สถานการณ์ข้ามโมดูล | Spring Modulith `Scenario` | การทำงานข้ามโมดูลในธุรกรรมเดียว | บทโมดูลใน SDS | วางแผน |
| สัญญาการเชื่อมต่อ | ชุดทดสอบหนึ่งชุดต่อ port พร้อม stub ที่จำลองความผิดพลาด | แต่ละ adapter ตาม port ของตน ทั้งหมดเวลา การปฏิเสธ ข้อความซ้ำ และระบบล่ม | บท Integration ใน SDS | วางแผน |
| ตั้งแต่ต้นจนจบ | Playwright | เส้นทางการทำงานของแต่ละบทบาททั้งภาษาไทยและอังกฤษ โดยคงสถานการณ์ของ sweep ไว้ | XC-TST-002 | วางแผน |
| โหลด | k6 | ช่วงโหลดสูงสุดวันที่ 30 กันยายน | XC-TST-003 | วางแผน |
| ความมั่นคงปลอดภัย | SonarQube, OWASP ZAP และการทดสอบเจาะระบบโดยผู้ทดสอบอิสระ | OWASP ASVS 5.0 ตามระดับใน ADR-0017 | ADR-0017 | วางแผน |
| การเข้าถึง | การตรวจอัตโนมัติและการตรวจด้วยโปรแกรมอ่านหน้าจอภาษาไทยโดยคน | ข้อกำหนดด้านการเข้าถึง | XC-TST-010 | วางแผน |
| รูปแบบติดตั้งและที่เก็บไฟล์ | การทดสอบของแต่ละรุ่นบนแต่ละรูปแบบ | รูปแบบติดตั้งที่รองรับทั้งสองแบบและผลิตภัณฑ์ที่เก็บไฟล์ทุกตัวที่ระบุไว้ | XC-TST-007, XC-TST-008 | วางแผน |
| ปิด AI | การรันอัตโนมัติ | ทุกโมดูลทำงานได้เมื่อปิด AI | XC-TST-009 | วางแผน |
| การซ้อมกู้คืน | การกู้คืนตามขั้นตอนที่กำหนด | ตัวเลขการกู้คืนและการกู้คืนหน่วยงานเดียว | XC-AVL-002, XC-AVL-003, XC-AVL-008 | วางแผน |

## การสอบย้อน {#ver-trace}

ผู้อ่านต้องตามเส้นทางเดียวจากกฎหมายไปถึงการทดสอบได้ สายนี้มีสี่ช่วง และสองช่วงสุดท้ายยังมีเพียงบางส่วน

| ช่วง | ที่เก็บ | วิธีตรวจ | สถานะ |
| --- | --- | --- | --- |
| ข้อกฎหมายถึงข้อกำหนด | ทะเบียนข้อกฎหมายใน `docs/spec/src/law/` และคอลัมน์ Clause ของแต่ละแถว | ตารางความครอบคลุมในภาคผนวกและไฟล์ `Fisko-clause-coverage.csv` ซึ่งสร้างพร้อมเอกสารนี้ | มีแล้ว แต่ข้อกฎหมายยังต้องยืนยัน |
| ข้อกำหนดถึงการออกแบบ | คอลัมน์ข้อกำหนดในตารางของ SDS ตารางจับคู่กฎ ความเห็น `covers` และบรรทัด `law` ของแผนภาพ | รหัสเป็นลิงก์ และการสร้างเอกสารแจ้งเตือนเมื่อย่อหน้าอ้างรหัสที่ไม่มีอยู่ | มีแล้ว |
| ข้อกำหนดถึงการทดสอบ | ปัจจุบันคือคอลัมน์ Prototype และหัวข้อหลักฐานการทดสอบของแต่ละบท ในระบบจริงการทดสอบแต่ละรายการต้องระบุข้อกำหนดของตน (XC-TST-004) | `Fisko-SRS-rtm.csv` แสดงข้อกำหนดทุกข้อ และการจับคู่การตรวจใน sweep กับการทดสอบระบบจริงอยู่ในหัวข้อการออกแบบการทดสอบของแต่ละบทโมดูลใน SDS | บางส่วน |
| การทดสอบถึงผลลัพธ์ | รายงานจาก CI เมื่อมีการทดสอบระบบจริงแล้ว | วัดความครอบคลุมข้อกำหนดจากรายงานเหล่านั้น (ADR-0017) | วางแผน |

## การรักษาความถูกต้องของสถานะ {#ver-honest}

คอลัมน์สถานะมีประโยชน์เมื่อเชื่อถือได้เท่านั้น แนวทางการเขียนกำหนดกฎต่อไปนี้สำหรับทุกบท

1. แถวเป็น `Prototyped` ได้ต่อเมื่อมีพฤติกรรมนั้นจริงและมีการตรวจเฉพาะใน `tests/sweep.js` หรือโค้ด end-to-end ครอบคลุม โดยคอลัมน์ Prototype ระบุการตรวจนั้น
2. แถวเป็น `Partial` เมื่อมีพฤติกรรมเพียงบางส่วน หรือมีครบแต่ไม่มีการตรวจเฉพาะ
3. แถวเป็น `Planned` เมื่อยังไม่มีพฤติกรรมนั้น
4. การเปิดหน้าใน sweep ไม่ทำให้สถานะของแถวสูงขึ้น เพราะแสดงเพียงว่าหน้าแสดงผลได้ และไม่บอกว่าหน้านั้นทำงานถูกต้อง
5. ขั้นตอนสาธิตหรือขั้นตอน end-to-end ที่ไม่มีการตรวจผลไม่ทำให้สถานะสูงขึ้น เช่นเดียวกับการเริ่มเอเจนต์โดยไม่ตรวจผล
6. การเดินผ่านขั้นตอนที่สั่งงานแล้วไม่ตรวจผลภายหลัง ไม่นับเป็นหลักฐานของงานนั้น
7. ข้อกำหนดเกี่ยวกับเซิร์ฟเวอร์ ฐานข้อมูล หรือเครือข่ายเป็น `Prototyped` ไม่ได้ เพราะต้นแบบทำงานบนเบราว์เซอร์เท่านั้น
8. ถ้าการตรวจที่ระบุไว้ถูกลบหรือถูกลดทอน แถวนั้นต้องลดเป็น `Partial` ในการแก้ไขเดียวกัน (ข้อเสนอ)

> [!OPEN] ยังไม่มีบุคคลที่สองทบทวนสถานะ เจ้าของผลิตภัณฑ์ต้องกำหนดผู้ทบทวน และต้องกำหนดค่าที่จะใช้แทนสถานะทั้งสามเมื่อเริ่มเขียนโค้ดจริง เนื่องจากค่าทั้งสามอธิบายต้นแบบเท่านั้น

## สิ่งที่สถานะพิสูจน์ได้และพิสูจน์ไม่ได้ {#ver-proof}

สถานะมาจากการอ่านโค้ดและการทดสอบ และไม่ได้รัน sweep เพื่อกำหนดสถานะ จึงต้องอ่านโดยคำนึงถึงข้อนี้

สถานะแสดงสิ่งต่อไปนี้

- `Prototyped`: ผู้อ่านพบพฤติกรรมนั้นในโค้ดต้นแบบ และพบการตรวจที่จะแจ้งข้อผิดพลาดถ้าผลลัพธ์ผิด
- `Partial`: ผู้อ่านพบพฤติกรรมบางส่วน หรือพบครบแต่ไม่มีการตรวจเฉพาะ หลายแถวจะสูงขึ้นได้ด้วยการเพิ่มการตรวจหนึ่งรายการโดยไม่ต้องเพิ่มความสามารถใหม่
- `Planned`: ผู้อ่านไม่พบพฤติกรรมนั้น แถวนี้จึงเป็นเป้าหมายการพัฒนา

สถานะไม่ได้แสดงสิ่งต่อไปนี้

- ไม่ได้แสดงว่าการตรวจผ่านในวันนี้ เพราะเป็นการอ่าน และไม่ได้รันการตรวจใดสำหรับฉบับนี้
- ไม่ได้แสดงว่ามีโค้ดสำหรับใช้งานจริง เพราะไม่มีส่วนใดเป็นโค้ดจริง
- ไม่ได้บอกอะไรเกี่ยวกับเซิร์ฟเวอร์ ฐานข้อมูล เครือข่าย โหลด การแยกข้อมูลหน่วยงาน หรือการกู้คืน เพราะ sweep ทำงานบนเบราว์เซอร์ด้วยข้อมูลตัวอย่าง
- ไม่ได้แสดงว่าพฤติกรรมนั้นถูกต้องตามกฎหมาย เพราะการอ้างข้อกฎหมายยังต้องได้รับการยืนยันตามที่แถวในทะเบียนระบุ
- ไม่ได้แสดงว่าการปฏิเสธทำงานได้ เว้นแต่มีการตรวจระบุไว้ บทงบประมาณบันทึกว่าไม่มีการตรวจใน sweep ที่ทดสอบการปฏิเสธตามกฎ และบทจัดซื้อจัดจ้างบันทึกว่าไม่มีการตรวจการปฏิเสธตามกฎแยกหน้าที่
- ไม่ได้แสดงว่าทุกโปรไฟล์ของหน่วยงานทำงานได้ เพราะ sweep ใช้โปรไฟล์จากข้อมูลตัวอย่าง ความสามารถที่ปิดอยู่ในโปรไฟล์นั้นจึงไม่แสดงผล
- ไม่ได้แสดงปริมาณงานที่เหลือ เพราะจำนวนแถวไม่ใช่ตัววัดแรงงาน และขนาดของแต่ละแถวต่างกันมาก
